# План раздельной реализации: фронтенд и бэкенд по контракту

Этот документ собирает в одном месте решения карты [«Карта: TypeSpec-контракт и план разделения фронтенда и бэкенда»](https://github.com/SevyConst/ai-for-developers-project-386/issues/10). Он **ничего не решает заново**: у каждого утверждения есть ссылка на ADR или тикет, где оно принято. Нашли расхождение между планом и тикетом: остановитесь, выясните, что верно, и поправьте план (см. раздел 11 про уже известные расхождения).

Состояние плана: контракт готов (коммит `c33c0de`), реализации нет. Термины предметной области (Владелец, Гость, Админка, Тип события, Окно записи, Слот, Бронирование, Звонок) — из [`CONTEXT.md`](../../CONTEXT.md).

## 1. Идея

Контракт — единственный источник правды на границе фронтенда и бэкенда (подход Design First). Аналогия из Java: **контракт — это интерфейс**, **бэкенд — его реализация**, **фронтенд — клиент**, который до готовности реализации работает с заглушкой. Фронтенд и бэкенд не ждут друг друга: оба строятся на типах, сгенерированных из одного и того же `contract/openapi.yaml`, а соответствие реальности проверяется на стыке вручную.

Работа идёт одним исполнителем линейной очередью (раздел 6). Реализация режется на **срезы** (одна возможность целиком), внутри среза два независимых **трека** (фронтенд и бэкенд, отдельные PR), и срез закрывается **контрольной точкой** (ручная проверка на настоящем стеке).

## 2. Исходное состояние (на `c33c0de`)

Есть:

- `contract/`: `main.tsp`, `openapi.yaml`, `tspconfig.yaml`, `package.json` и `package-lock.json` (точные `@typespec/*` 1.17.0). Шесть операций под `/api`, 19 схем, OpenAPI 3.0.0.
- CI: задачи `contract` (компиляция, формат, свежесть `openapi.yaml`) и `node-version` (сверка `.nvmrc`, `backend/pom.xml`, `Dockerfile`). `.nvmrc` лежит в корне.
- ADR-0001…0004 в `docs/adr/`, раздел про `contract/` в [`AGENTS.md`](../../AGENTS.md).
- Бэкенд: Spring Boot 4.1, Java 25, только скелет шаблона — `HelloController` (`/api/hello`), `Greeting`, `HelloControllerTest`.
- Фронтенд: React 19 + Vite 8, страницы `/` (главная), `/book` (заглушка) и 404; `/admin` намеренно не реализован; `src/lib/api.ts` с `fetchGreeting` (нигде не вызывается).

Нет (всё это делает очередь работ): плагина генератора серверных интерфейсов, `spring-boot-starter-validation`, Orval, MSW, SPA-fallback, `COPY contract/openapi.yaml` в `Dockerfile`, хранилища данных.

## 3. Контракт

### 3.1. Где живёт, как генерируется и проверяется

Решение и обоснование: [ADR-0003](../adr/0003-contract-in-repo-root.md), тикет [«Расположение контракта, генерация и сборка»](https://github.com/SevyConst/ai-for-developers-project-386/issues/18).

- Контракт на TypeSpec лежит в `contract/main.tsp`; результат — `contract/openapi.yaml`, **единственный сгенерированный файл, который коммитится**. Руками его не правят.
- Генерирует разработчик локально: `cd contract && npm ci && npx tsp compile .`. Проверка перед коммитом: `npm run check` (то же, что в CI). `.tsp` удобно править в VS Code с расширением TypeSpec.
- Свежесть проверяет задача CI `contract`: перегенерация и `git diff --exit-code`. Maven и Docker `tsp` **не запускают**, а читают готовый файл.
- Код потребителей (Java-интерфейсы бэкенда, TypeScript-клиент фронтенда) генерируется из `openapi.yaml` в сборке и **не коммитится**.
- Версии `@typespec/*` закреплены точно: вывод эмиттера между версиями побайтно не гарантирован. Обновление TypeSpec — осознанный шаг: поднять версии, перегенерировать, закоммитить `openapi.yaml`.
- Версия OpenAPI — 3.0.0 (`openapi-generator` читает 3.0 без оговорок, 3.1 помечает как beta, 3.2 не читает) — [ADR-0004](../adr/0004-server-interfaces-generated-from-contract.md), [«Стек потребления контракта…»](https://github.com/SevyConst/ai-for-developers-project-386/issues/21), п. 1.
- Единая версия Node — корневой `.nvmrc`; `<node.version>` в `backend/pom.xml` и тег `node:` в `Dockerfile` совпадают с ним вручную, расхождение роняет CI.

### 3.3. Как менять контракт во время работы

Источник: [«Стек потребления контракта…»](https://github.com/SevyConst/ai-for-developers-project-386/issues/21), п. 6.

1. **Кто правит.** `.tsp` и `openapi.yaml` меняются только отдельным коммитом или PR с типом `feat(contract)`, `fix(contract)` и т. п. (ломающая правка — `feat(contract)!:`). Не вносите правку контракта молча внутри PR фронтенда или бэкенда.
2. **Порядок.** Правка контракта вливается в `main` раньше реализаций; обе стороны подтягивают её перебазированием. Если фронтенд-трек обнаружил, что контракта не хватает: остановиться, внести правку контракта, перегенерировать `openapi.yaml`, продолжить.
3. **Согласование.** Ревью PR автором проекта. Рассинхрон ловят сборка (`tsc` на клиенте, `javac` на интерфейсах) и задача CI `contract`.
4. **Версионирования нет.** Фронтенд и бэкенд выходят одним jar, внешних потребителей нет; `info.version` — константа `1.0.0`. Ломающая правка допустима, если в той же серии PR обе стороны исправлены.

## 4. Как стороны работают независимо

Все решения: [«Стек потребления контракта…»](https://github.com/SevyConst/ai-for-developers-project-386/issues/21) и [ADR-0004](../adr/0004-server-interfaces-generated-from-contract.md).

### 4.1. Фронтенд до готовности бэкенда

- **Клиент.** Orval 8.42.0 (точная версия), `client: 'fetch'`, вывод по тегам в `frontend/src/api/generated/` (каталог под `.gitignore`), без `mutator`. Генерируется `pre*`-хуками npm перед `dev`, `build`, `typecheck`, `test` (аналог привязки плагина генератора к фазе `generate-sources` в Maven). Результат вызова — дискриминируемое объединение `{ data, status, headers }`: ветки 400/404/409 сужаются по `status`, `code` в них — закрытое объединение.
- **Правило:** API вызывается только сгенерированным клиентом из `src/api/generated`, ручной `fetch` не используется. `src/lib/api.ts` удаляется в шаге 0.3.
- **Мок.** MSW 3 (точная версия): один набор обработчиков и в Vitest (`setupServer` в `setupFiles`, сценарии через `server.use(...)` — аналог `@MockBean` в тесте), и в браузере по скрипту `npm run dev:mock` (`vite --mode mock`; аналог `@Profile("mock")`: в сборке его нет). Браузерный мок — один небольшой фейк в памяти в `frontend/src/mocks/` на типах Orval: детерминированный календарь на 14 дат с `+03:00`, без воспроизведения правил Слотов и порядка проверок 409 (это проверяет бэкенд, фронтенд реагирует только на `code`).
- **Не используются:** Prism (заготовки без состояния, лишний процесс, уязвимости в `npm audit`) и моки Orval (данные не соответствуют контракту).

### 4.2. Бэкенд до готовности фронтенда

- **Интерфейсы из контракта.** `openapi-generator-maven-plugin` 7.26.0 (точная версия), генератор `spring`: `interfaceOnly`, `skipDefaultInterface=true`, `useTags`, `useSpringBoot4`, `useJackson3`, `openApiNullable=false`; вход `../contract/openapi.yaml`, фаза `generate-sources`, результат в `target/generated-sources`. Получаются `EventTypesApi` и `BookingsApi`; контроллеры делают `implements` (аналог реализации интерфейса, сгенерированного из WSDL). Операция, пропущенная в контроллере, не компилируется. Сгенерированные модели — только DTO на границе API, доменные классы пишутся отдельно.
- **Время в DTO — `String`** (`typeMapping OffsetDateTime=String`): иначе любой `POST` с таким телом падает с 500 (`HV000030`). Маппер строки во время и обратно с явным `+03:00` — задача бэкенда.
- **Ошибки.** `@RestControllerAdvice` возвращает только сгенерированные модели ошибок, не Spring `ProblemDetail`; нужен `spring.jackson.default-property-inclusion=non_null`.
- **Контрактные тесты.** `openapi-request-validator-mockmvc` 3.0.0 (точная версия, test-scope) в `@WebMvcTest` + `MockMvcTester`: `openApi().isValid(validator).match(result.getMvcResult())`. Тесты проверяют статус и `code` каждого отказа, порядок проверок 409, ровно 14 дат в календаре Слотов (включая пустые), 400 для `page` и `pageSize` в обоих списках. Негативные тесты используют `LevelResolver` с `withLevel("validation.request", IGNORE)`.
- **Вручную остаётся то, что генератор теряет:** кратность 15 минут (`not_on_grid`), мапперы времени.

## 5. Определения

- **Срез** — одна возможность целиком (например, «Типы событий»): её экран и её эндпоинты.
- **Трек** — одна из двух независимых половин среза: фронтенд (FE) или бэкенд (BE), каждая отдельным PR.
- **Контрольная точка (КТ)** — ручная проверка среза на настоящем стеке после того, как влиты оба трека.

Это процессные термины, в `CONTEXT.md` они не входят. Порядок треков в каждом срезе: **FE первым** (против мока), затем BE (против контрактных тестов). Довод: если фронтенду не хватит контракта, правка дешевле, пока реализован только мок.

**Что входит во FE-0:**

- MSW 3 точной версии. В Vitest: `setupFiles` с `setupServer`, сброс обработчиков между тестами.
- Браузерный мок: плагин `msw/vite` в `vite.config.ts`, `dev:mock` = `vite --mode mock`, в `main.tsx` условный динамический импорт `virtual:msw` под `import.meta.env.MODE === 'mock'`, каталог `src/mocks/` с одним обработчиком `listEventTypes` (фикстура на типах Orval), `/// <reference types="msw/vite/client" />`.
- **Сторож в CI:** в задаче `frontend` шаг `npm run build` и `test ! -e dist/mockServiceWorker.js`.
- `COPY contract/openapi.yaml /app/contract/openapi.yaml` в стадию `frontend-build` `Dockerfile`.
- Удаление `frontend/src/lib/api.ts` (`fetchGreeting`), правка `AGENTS.md`: правило «API вызывается только сгенерированным клиентом», команда `dev:mock`.

**Что намеренно не входит в BE-0** (уходит в BE-трек S1): `@RestControllerAdvice`, `spring.jackson.default-property-inclusion=non_null`, валидатор `openapi-request-validator-mockmvc`, `LevelResolver`, удаление `Hello*`. Причина: четыре исключения Spring возникают только на настоящих эндпоинтах, а S1 вызывает все четыре (тело `POST`, `page` и `pageSize`, UUID в пути). В нуле остаётся только то, что проверяется сборкой.

`Dockerfile` правится двумя независимыми строками, по одной в своей стадии, поэтому BE-0 и FE-0 не конфликтуют.

| Ф.1 | Уборка мока | Убрать браузерный мок целиком: `dev:mock` и `predev:mock`, плагин `msw/vite`, строку `msw/vite/client`, ветку `MODE === 'mock'` в `main.tsx`, браузерные файлы в `src/mocks/`, сторож в CI. MSW в Vitest остаётся. Правка `AGENTS.md`. |
| Ф.2 | Приёмка | `docker build` + `docker run`. Сквозной сценарий: Владелец создаёт Тип → Гость бронирует → Владелец видит Звонок. F5 на `/admin` и `/book`. Воркера в jar нет (`unzip -l`). |

## 7. Переход от мока к реальности

**Всё или ничего.** Браузерный мок остаётся полным и согласованным до конца: в браузере это один фейк на типах Orval, при устаревании ответа ругается компилятор. На стыке обработчики **не удаляются**, BE-PR не трогает файлы фронтенда. Стык — контрольная точка; нашлось расхождение — чинится в PR той стороны, которая виновата. После S4 мок убирается целиком (Ф.1). Vitest-сценарии (`server.use`) и браузерный фейк — разные наборы обработчиков, их жизни не связаны.

Автоматического сквозного теста (Playwright и т. п.) нет: ответы сервера сверяют контрактные тесты бэкенда, а клиент и мок фронтенда строятся на типах из того же контракта. Режим `dev:mock` переключает на реальность не человек по срезам, а Ф.1 один раз в конце.

Причина «всё или ничего»: если удалять обработчики по мере реализации, то после стыка S1 фронтенд S2 ходил бы в настоящий бэкенд и перестал бы быть независимым от него.

## 8. Правила на всех шагах

- **Контракт** меняется только по правилам п. 3.3.
- **Коммиты** — Conventional Commits. Конфигурационные PR — `chore`, функциональные — `feat`, SPA-fallback — `fix`. `CHANGELOG.md` и версию не трогать (их ведёт `release-please`).
- **Шаг закончен** только при зелёном CI: `checkstyle:check`, `mvnw test`, `npm run lint -- --max-warnings=0`, `typecheck`, `test`, задачи `contract` и `node-version`.
- **Словарь** — из `CONTEXT.md`: не писать «встреча», «вид брони», «запись» вместо Звонок, Тип события, Бронирование. Идентификаторы в коде на английском, русские термины сопоставлены им в [«Форма API…»](https://github.com/SevyConst/ai-for-developers-project-386/issues/17), п. 4.
- Нужен новый предметный термин: сразу внести в `CONTEXT.md` (только глоссарий).

## 9. Ловушки

Известные грабли, на которые уже наступили при подготовке плана.

- **`onUnhandledFrame`, не `onUnhandledRequest`.** В MSW 3 опция переименована. TypeScript это ловит, Vitest — нет.
- **Checkstyle и `generate-sources`.** Сгенерированный код не проходит Checkstyle (263 замечания). Отдельный `./mvnw checkstyle:check` (как в CI) его не проверяет; если привязать Checkstyle к фазе после `generate-sources`, нужен `excludes` для каталога генерации.
- **`@Pattern` на `OffsetDateTime` падает в рантайме** (`HV000030`): время в DTO — `String`.
- **Негативные контрактные тесты требуют `LevelResolver`** с `withLevel("validation.request", IGNORE)`: иначе валидатор помечает ошибкой сам плохой запрос, хотя проверяется ответ.
- **Jackson 3 приводит входящее `+03:00` к UTC.** На строковых DTO это не влияет; если когда-нибудь DTO станут `OffsetDateTime`, нужны две неочевидные настройки (см. «Considered Options» в ADR-0004).
- **Коэрция Jackson** (`30.5` молча становится 30, `123` — `"123"`) должна быть выключена; настройки не проверялись, их проверяют тесты S1.
- **Воркер MSW не должен попасть в jar.** Раньше предполагалось положить `mockServiceWorker.js` в `public/`; от этого отказались: воркер раздаёт плагин `msw/vite`, а страховка — сторож в CI (шаг 0.3).
- **Порядок фаз Maven.** `generate-sources` идёт раньше `generate-resources` (там `frontend-maven-plugin`); `-Dskip.installnodenpm -Dskip.npm` из `Dockerfile` отключает только npm-шаги и генератору не мешает.
- **`.dockerignore` исключает `docs/`**: контракт и всё, что нужно сборке, лежит вне `docs/`; сам этот документ в образ не попадает, так и задумано.
- **SPA-fallback не должен перехватывать `/api/**`**: неизвестный путь под `/api` остаётся честным 404.

## 10. Предпосылка: хранилище

Выбор хранилища данных вне карты (это реализация, не контракт), но шаг 1.2 первым нуждается в состоянии (реестр Типов событий) и без решения не стартует. План **его не принимает**.

**Перед шагом 1.2 нужно принять решение о хранилище отдельным тикетом или ADR.** Заметка для того решения: S2 и S3 строят Слоты и конфликты Бронирований на тех же данных.

## 11. Расхождения с другими документами (чинятся по ходу очереди)

- **ADR-0001, срок SPA-fallback.** В ADR сказано «в тикете страницы записи». По плану это шаг 0.2, до первой настоящей страницы (`/admin` в S1). В шаге 0.2 в ADR-0001 дописывается строка о переносе срока. Тикет-источник: [«Нарезка реализации…»](https://github.com/SevyConst/ai-for-developers-project-386/issues/22), п. 7.
- **Переходный период мока.** В [«Стеке потребления контракта…»](https://github.com/SevyConst/ai-for-developers-project-386/issues/21), п. 4 сказано «обработчик операции удаляется, когда она реализована на бэкенде». Заменено правилом «всё или ничего» (раздел 7).
- **`mockServiceWorker.js` в `public/`.** Ловушка из п. 4 того же тикета снята (раздел 9).
- **Нулевой срез.** Тот же тикет передавал в нулевой срез `@RestControllerAdvice`, валидатор и `LevelResolver`; по плану они уходят в BE-трек S1.
- **`AGENTS.md`.** Пока там написано «Вызовы API на фронтенде идут через `frontend/src/lib/api.ts`» и в качестве примера одного теста назван `HelloControllerTest`. Правится: правило про сгенерированный клиент и команда `dev:mock` — в шаге 0.3, пример теста — в шаге 1.2, удаление `dev:mock` — в Ф.1.

## 12. Что не проверялось

Эти пункты проверяются шагами очереди (в «Готово, когда» они учтены):

- реальный прогон задач CI `contract` и `node-version` на GitHub;
- настройки Jackson против коэрции значений (S1, тесты бэкенда).

## 13. Вне плана

Реализация этого списка не планируется; он ограничивает объём ([карта](https://github.com/SevyConst/ai-for-developers-project-386/issues/10), раздел «Out of scope»):

- редактирование и удаление Типов событий;
- отмена и перенос Бронирования;
- уведомления Гостю или Владельцу;
- настройка рабочих часов Владельцем (все часы рабочие);
- защита Админки (авторизации нет по условию);
- визуальный дизайн экранов и макеты;
- выбор хранилища как часть контракта (но см. предпосылку в разделе 10).
